# Budget et Compte — Run Doc (dev preview)

Local-first family finance PWA. Vite 5 + React 18 + TypeScript + Tailwind 3. No backend, no `.env` files — all data lives in the browser's localStorage.

## 1. Reproduce the artifacts

```bash
cd /Users/babacar/Downloads/patrifamille-app
npm install          # dependencies only; nothing to copy from elsewhere
```

No env files or API keys are needed to run the app. One **optional** file exists: `.env.local` holding `VITE_SHOP_URL=http://127.0.0.1:8790` turns on the “Acheter par Wave ou Orange Money” button in Réglages → Offre & licence (see §2, *The shop, locally*); delete the file (or blank the variable) and the button disappears, leaving the “paste your key” form. The URL is public — the file holds no secret, and no other procedure depends on it. PWA artifacts are **build-generated** by `vite-plugin-pwa` (service worker + manifest injection into `dist/`); the PNG icons in `public/icons/` are generated from `public/icons/icon.svg` and only need regeneration if that SVG changes. The artwork is the wallet motif plus the brand monogram **BC** (Budget et Compte); the maskable PNG is generated from that same `icon.svg` by the preset, which pads it into the safe zone itself — the old hand-drawn `maskable-icon.svg` reference was removed as unused.

```bash
npm run pwa-assets   # regenerates public/icons/*.png + favicon.ico (config: pwa-assets.config.ts)
```

Brand check after a rename (the brand is `Budget et Compte` — see the decision log): the first command must print **nothing**, the second must list every surface that carries the name.

```bash
grep -rn "Comptes & Budgets" --include="*.ts" --include="*.tsx" --include="*.html" --include="*.json" --include="*.md" . | grep -v node_modules
grep -rln "Budget et Compte" index.html vite.config.ts src/i18n/translations.ts public/icons/*.svg STORE_LISTING.md
```

**Branch protection (ruleset "main requires verify", id 23183182).** `main` requires the `verify` check green before anything lands — **with no bypass, not even for the owner** — plus deletion and force-push protection. Consequence that matters day-to-day: **direct pushes to `main` are refused** unless GitHub has already run `verify` on those exact commits, so the flow is branch → PR → green `verify` → merge (the merge then triggers the deploy). The CI workflow runs on `pull_request` for this reason. The local pre-push gate was retired when the ruleset landed — a server-side rule beats a bypassable local hook; a local full-gate run before pushing remains useful as a courtesy, not a gate. The first push after the ruleset was created was blocked by it, live, as the proof.

### App walkthrough (fresh localStorage)

1. Lock screen → set password (min 6 chars) → creates the encrypted vault (AES-GCM 256, key derived via PBKDF2 from the password)
2. Data at REST is ciphertext only: localStorage holds `patrifamille_fcfa_vault_v1` (`pfvault1$salt$iv$ct`) + `patrifamille_sec_v1` (non-secret config + password verifier). Pre-encryption installs migrate transparently on first unlock.
3. Dashboard: net worth = assets − loan (loans count negatively); Mobile Money wallets (Wave / Orange Money / MTN MoMo) render with brand badges
4. Transactions tab: filters, CSV export, add/edit/delete with validation — balances derive from the ledger instantly
5. Auto-lock: session locks after 5 idle minutes (config default); locking drops the in-memory key, so a locked session cannot read data
6. Password change (Réglages): re-encrypts the vault under a new key BEFORE swapping the password verifier — a failed re-encryption leaves the old password working
7. Dashboard also lists savings goals (progress, amount left, deadline); adding a 2nd goal on the free offer opens the Pro upsell, which links to Réglages → Offre & licence
8. Languages: fr / en / es (Réglages → Langue & apparence), detected from the browser on first run and persisted in `patrifamille_prefs_v1` alongside the theme (dark default, light toggle). Amounts and month/date labels follow the language locale; the light theme flips the whole slate palette via CSS variables (`html.light`). Restart the dev server after changing `tailwind.config.js` — the CSS-var palette only takes effect on a fresh build
9. Packs pays: the catalog lists 5 country packs. On the free offer install one (the others' Install buttons are disabled and an upsell banner appears); install Sénégal on Pro and the card opens three tools — a net-pay estimator (250 000 gross → 14 000 retirement + 7 500 health, taxable base 175 000, income tax 30 833, net 197 667, “Total retenu : 20.9 %”), the school-fee table, and the budget template whose income field is pre-filled with the ledger's own 3-month average income. “Créer les catégories” writes 8 real categories into the Budget tab; “Retirer ces catégories” takes them back out (verified in the Budget tab both ways)
10. Buying Pro (only when a shop is configured, i.e. `.env.local`): Réglages → Offre & licence shows **Acheter par Wave ou Orange Money**, whose link carries the country derived from the currency preference (`XOF` → Sénégal, `XAF` → Cameroun) → the shop page lists both plans and the country's operators → the buyer pays on CinetPay's page (the local rehearsal simulates it at `/payer`) → the key arrives by e-mail → pasting it in **Clé de licence** activates Pro, verified by signature on the device. Without a shop, the block is absent and the key form is the only path, which is how licences sold by hand work
11. Missing notification (the failure the cron exists for): `curl "http://127.0.0.1:8790/dev/paid?ref=<ref>"` marks the order paid **at the operator without sending the webhook** — `/api/order` stays `pending`, the buyer has paid and has nothing. `curl "http://127.0.0.1:8790/dev/reconcile?grace=0"` runs the scheduled job by hand and answers `{"checked":1,"delivered":1,…}`; the order flips to `delivered` and the key is at `/dev/mail`. Run it again: `{"checked":0,…}` — terminal orders are never queried twice, and no second e-mail goes out
12. ⚠️ Forgetting the password means the data is UNRECOVERABLE by design (no backdoor, no reset) — clear site data to start over

**Maintainer note — one write path.** Every mutation in `src/App.tsx` goes through `mutate((current) => next)`, which reads `dataRef.current` — never the render-time `data` — and hands the result to `persist`, the only writer (memory + vault + sync). That is what lets a handler perform several writes in a row: the second write sees the first, which the older mixed idiom did not guarantee (it once silently dropped a saved tontine member when that member's rounds were recomputed in the same tick). `reencryptVault` reads the same ref for its snapshot.

**Informed overwrites.** Neither sync surface replaces data on a bare click: a pull that changed something and a conflict restore are both staged behind a confirm card (`SyncView`) that shows `backupSummary` of the resulting data — the same counts as a backup import. The restore card appears **before** `engine.restore()` runs, thanks to `SyncEngine.previewRestore(id)`, a read-only projection of the engine's records (a restore propagates to every device the instant it runs, so it must be previewed, not staged after the fact). A declined pull is safe by design: the engine commits its merge internally, and the next edit re-enters the exchange as an ordinary local change. Leaving Réglages with a card open changes nothing.

The rules the handlers apply — upsert-vs-append, the tontine delete cascades, pack install/uninstall, whole-state restore, the payout no-op on an absent round — no longer live in `App.tsx`: they are the pure `AppData → AppData` functions of **`src/services/dataEdits.ts`**, pinned by `dataEdits.test.ts`. The write path itself — the single reader, the single writer, the side-effect seam — is **`src/hooks/useDataStore.ts`** (`createDataStore` + the `useSyncExternalStore` binding), pinned by `useDataStore.test.ts` including the two-writes-in-one-handler case. `App.tsx` only wires the two together: `store.bindEdit(edit)` for every handler, `onPersist` = sync publish + vault write, `set` on unlock/sync-pull, `clear` on lock — so the tested code is the code that runs. The only edit taking a renderer is `applyPackTemplate`, because category names are UI text in the current language. To change a mutation rule, edit `dataEdits.ts`; to change how writes flow, edit `useDataStore.ts` — not the component.

## Decision log

**The shop: policy is data, and the signing key never ships.** `purchase/core.js` holds every decision (prices, the notify-token check, the amount/currency rules, expiry, the receipt) and is pure — no fetch, no storage, no environment — so it is unit-tested directly, while `worker.js` is a thin shell over it. A webhook is unauthenticated HTTP until proven otherwise, so delivery needs **two** independent facts: the notify token CinetPay returned when the payment was created (compared in constant time) *and* an **authoritative status re-query** — the amount is never read from the notification body, which is what stops a spoofed or underpaid payment from minting anything. `isPaidStatus` lets an explicit textual status overrule the numeric codes, because in the v1 API `code: 100` means the *request* succeeded on a payment that may have failed (a case with its own test). Minting is **deterministic** from the stored order, so a repeated webhook cannot produce a second, different licence even before the `delivered` flag is read. The app is not involved in any of it: it only *links* to the shop (`src/services/shop.ts`), so buying never adds a server call to the app. (The one feature that does reach out is multi-device sync, which is opt-in and E2E-encrypted — the relay stores one opaque blob. Any claim of “no server” in the product copy must be read with that exception, or it is false.)

**The webhook is not trusted to be the *only* way a payment arrives (reconciliation cron).** A webhook can be lost — CinetPay's retries stop after a while, and a deploy during the callback drops the notification — and the buyer's money has already left their account, so "no notification" must not mean "no licence". Every 15 minutes the Worker walks the orders still waiting for money (KV `list` metadata filters the terminal ones without a value read) and re-asks CinetPay. Three properties make it safe: it has **no untrusted input** (no webhook body, and the notify token is not needed — it starts from an order only we stored), it shares the single `moneyVerdict` rule with the webhook so the two paths can never disagree, and a status it cannot fetch means *wait*, never *deliver* — money is never assumed. The 10-minute grace period is what keeps it cheap and idempotent; delivering is deterministic, so a late cron that races a webhook mints the same key. Covered by tests (`tests/purchase.test.ts`, `tests/purchaseWorker.test.ts`) and rehearsed live with `/dev/paid` + `/dev/reconcile` on the harness.

**The checkout is in French only.** CinetPay's own page is French for every market we sell in, the licence lives in a French-branded product, and a translated checkout buys nothing but ambiguity about what is being paid for. The pages are `lang="fr"` deliberately; the *app* stays trilingual. Revisit only if a market appears where the operator flow is not French.

**Brand: `Budget et Compte`, in French in every locale (settled).** It is a proper name, not a label, so it is **never translated**: the `fr`/`en`/`es` dictionaries all carry the same `app.brand`, and the English and Spanish UIs keep the French name on purpose. The only surfaces that hold it are `index.html` (title + `apple-mobile-web-app-title`), the manifest in `vite.config.ts` (`name` + `short_name`), the three dictionaries, the About screen (which reads `t('app.brand')`, so it follows automatically), the icon artwork, and `STORE_LISTING.md`. A rename touches exactly those; verify with the grep in the Reproduce section above, then `npm run pwa-assets` if the artwork changed. The manifest has no `id`, so a rename updates an already-installed PWA in place (identity falls back to `start_url`, which did not change).

**Country pack figures are indicative, by design.** The salary/school numbers in `PACKS` (`src/services/packs.ts`) are transcribed templates for *household planning*, not a payroll engine: every pack carries the year it was transcribed (`asOf`), every pack tool prints a disclaimer, and “Estimateur de salaire net” is worded so nobody mistakes the result for a payslip. Update them in **one place** (`PACKS`) when a finance law changes, bump `version`, and every screen follows — no component holds a rate. Content gating: **one pack on the free offer**, all packs on Pro/association; an installed pack is never hidden when a licence lapses, the same rule as savings goals and the tontine module.

**Deployment: GitHub Pages from CI (the repo is public); the Cloudflare path was retired with the plan wall.** The repo started private, where Pages is plan-blocked (422) and the deploy targeted Cloudflare Pages with a two-secret setup; making the repo public unlocked Pages and removed every secret from the deploy path — the Cloudflare job, its setup script and its two (never-stored) secrets are gone. The workflow now deploys with the official Actions: verify builds with `VITE_BASE=/<repo>/` and uploads the tested `dist/`; deploy re-uploads it as a Pages artifact and publishes with `actions/deploy-pages` (OIDC — no token to rotate). Every push to `main` deploys. **The base path is load-bearing:** Pages serves a project site from `/<repo>/`, and `vite-plugin-pwa` derives the manifest identity (`start_url: './'`) and the service-worker registration (`/<repo>/sw.js`) from it. Rehearse locally: `VITE_BASE=/Budget-et-Compte/ npm run build`, then serve with the *same env* under `vite preview` — note that `vite preview` without `VITE_BASE` serves `index.html` for any subpath (its SPA fallback), which masks subpath errors. After each deploy, `scripts/smoke-test.sh` fetches the live URL and asserts **four** surfaces: the branded app shell, **the entry JS bundle the shell actually references** (extracted from the fetched HTML, host-absolute paths joined to the scheme+host; refuses HTML masquerades and empty bodies — the guard for the "white screen behind a 200 shell" class, e.g. a forgotten `VITE_BASE` subpath deploy), the webmanifest `name`, and the generated service worker, with retries that absorb propagation; markers were verified against `dist/` artifacts and the script rehearses against a local static server. **Rollback:** every run keeps the tested `dist/` as the `site` artifact for 7 days — download it (`gh run download <run-id> -n site`), then re-publish via a manual `workflow_dispatch` after temporarily pointing the deploy at the older bundle, or simpler: `git revert` the offending commit and let the pipeline redeploy the previous tested bytes. **Uptime between deploys:** `.github/workflows/uptime.yml` runs the same smoke script against the live URL every 6 hours (and on demand, with an optional `url` input for rehearsals); a failure opens an "Uptime failure" issue, continued failures append comments with run links, the next pass closes it as recovered, and the failing run itself goes red. Branching is deliberately in the shell on the script's exit code — a step-level `if: steps.<id>.outcome` was observed to skip its dependant on a real failure, which would silently drop the record; rehearsed end-to-end with a dead-URL dispatch (issue opened) followed by a production dispatch (issue closed as recovered). Note GitHub disables scheduled workflows after ~60 days of repo inactivity — ordinary development keeps this one alive. **Lighthouse 10 audit of the live site (2026-09-13, run twice): PWA category 1.0 both times** — `installable-manifest`, `service-worker`, `splash-screen`, `themed-omnibox`, `maskable-icon` (plus viewport/content-width) all pass; accessibility/best-practices/SEO also 1.0, performance 0.63–0.65 (the un-split main bundle, see the build's chunk warning — the one optimization worth doing). No build secret is needed: the app is 100% local, and the optional `VITE_SHOP_URL` (public localhost URL) is unset in production builds, which simply hides the buy button and leaves the paste-a-key form — the hand-sold-licence path.

**Custom domain (when attached).** `scripts/custom-domain.sh <domain>` wires it end to end: prints the registrar records (4× `A` apex → `185.199.108–111.153`, `CNAME www → vieuxniang.github.io.`), waits for propagation via `dig` against the four edge IPs themselves (what GitHub sees, not the local resolver), sets the repository variables (`SITE_URL=https://<domain>/`, `PAGES_BASE=/` — the workflows read them with the github.io defaults as fallback), attaches the domain via `PUT /pages` with `https_enforced=true`, and lands the `CNAME` file **through the protected flow** — branch → PR → `gh pr checks --required --watch` (only `verify` runs on PRs; the deploy job is gated to `main`) → merge, which itself triggers the root-relative build + deploy + live smoke. A re-run with `CNAME` already tracked and matching skips the PR and just dispatches a deploy. Direct pushes to `main` are refused by the ruleset (`main requires verify`, no bypass), which is why the commit takes a PR. The apex is canonical; `www` 301s to it. Old github.io URL keeps working via GitHub's redirect; the uptime monitor follows `SITE_URL` automatically. If the domain's DNS is on Cloudflare, records must be DNS-only (grey cloud) during setup so the Let's Encrypt HTTP-01 issuance reaches GitHub's edge.

**Signature scheme: ECDSA P-256 (settled).** Ed25519 was implemented first and reverted: native Ed25519 verification only exists from Chrome/Edge 137, so the very preview shell used here (Chrome 130) could not verify a license, and neither could older Android WebViews — a real share of the target market. P-256 is universally available, needs no dependency, and reuses `node:crypto`'s `webcrypto` on the minting side, so no scheme translation is needed. Cost of switching later: regenerating the keypair invalidates already-sold licenses, hence the freeze.
